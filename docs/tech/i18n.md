# i18n — système de traduction custom

L'application supporte le français (par défaut) et l'anglais (US-022). Un système léger, sans dépendance externe,
centralise tous les textes visibles afin d'éviter le texte en dur dans les templates et de permettre l'ajout
ultérieur d'autres langues.

---

## 1. Fichiers

- `frontend/public/i18n/fr.json` et `frontend/public/i18n/en.json` — un dictionnaire par langue, **structure
  strictement identique** (mêmes chemins de clés, mêmes paramètres `{{nom}}` par clé) ; `fr.json` reste toujours
  chargé en mémoire comme repli, même quand `en` est la langue active (RG-022-07)
- `frontend/src/app/core/i18n/translate.service.ts` — charge les dictionnaires, expose `translate(key, params?)`,
  le signal `language` (langue active) et le signal `loaded`
- `frontend/src/app/core/i18n/translate.pipe.ts` — pipe impur `translate`, standalone
- `frontend/src/app/core/language/` — `LanguageService` (préférence, aperçu, synchronisation avec `SettingsStore`),
  `language-storage.ts` (cache anti-flash `localStorage`), `provide-language.ts`

---

## 2. Structure des clés

Clés en `camelCase`, hiérarchie par écran puis par zone (voir `fr.json`/`en.json` pour la liste exhaustive à jour).
Extrait :

```json
{
  "common": { "save": "Enregistrer", "cancel": "Annuler", "ok": "OK" },
  "board": {
    "toolbar": { "refresh": "Rafraîchir", "settings": "Paramètres" },
    "filters": { "drafts": "Drafts", "mine": "Mes MRs", "count": "{{count}} MR{{countSuffix}} · {{projects}} projet{{projectsSuffix}}" },
    "mergeRequests": { "meSuffix": "(moi)" }
  },
  "settings": {
    "misc": { "theme": { "title": "Thème" }, "language": { "title": "Langue" } }
  }
}
```

Règles :
- Les enums sont traduits par concaténation : `{{ 'board.difficulty.' + mr.difficulty | translate }}`
- Les paramètres utilisent la syntaxe `{{name}}` et sont passés en second argument : `{{ 'board.ready.days' | translate: { days: 3 } }}`
- Les messages d'erreur des stores sont des clés (`'board.errors.load'`), traduits dans le template ou le snackbar
- **Exception** (RG-022-02) : les libellés des options du contrôle « Langue » (« Français » / « English ») sont des
  **endonymes en dur**, jamais des clés i18n — un utilisateur doit reconnaître sa langue quel que soit l'état
  courant de l'interface

## 3. Utilisation

```ts
@Component({ imports: [TranslatePipe, MatButtonModule], ... })
```

```html
<button mat-stroked-button>{{ 'board.toolbar.refresh' | translate }}</button>
```

Dans le code (snackbar, aria-label dynamique) : `inject(TranslateService).translate('board.errors.sync')`.

### Formats localisés

Les dates (`formatShortDate`, `formatDateTime` de `shared/format/format-date.ts`) et les séparateurs de milliers
(`formatThousands` de `shared/format/format-number.ts`) dépendent de la langue (RG-022-10) : ils prennent un second
paramètre `language`, à passer explicitement par l'appelant — jamais lu implicitement depuis un service :

```ts
formatShortDate(row.createdAt, this.i18n.language()); // '13/09/2026' (fr) ou '2026-09-13' (en)
formatThousands(value, this.i18n.language());          // '1 240' (fr) ou '1,240' (en)
```

`formatTime` (heure seule, `HH:mm`) ne prend **pas** ce paramètre : le format est identique dans les deux langues.

### Réactivité au changement de langue

`TranslateService.translate()` **lit le signal `language`** en tout premier, avant toute résolution de clé (même
sans utiliser sa valeur) :

```ts
translate(key: string, params?: TranslationParams): string {
  this.language(); // dépendance réactive : force le recontrôle de tout appelant
  const value = lookupTranslation(this.dictionary, key) ?? lookupTranslation(this.fallback, key);
  // …
}
```

Cette lecture est ce qui permet à un composant `OnPush` déjà stable — sans aucun `@Input` ni évènement changé — de
se rafraîchir quand la langue change ailleurs dans l'application (ex. depuis l'écran Paramètres), **quel que soit
le point d'entrée** : le pipe `| translate` du template (déjà impur, RG-022-12) aussi bien qu'un appel direct
`this.i18n.translate(...)` dans un `computed()` de composant, sans que ce `computed()` ait besoin de lire lui-même
le signal `language`.

⚠️ **Le correctif est volontairement centralisé ici, pas dans `TranslatePipe`** : une première version ne faisait
lire le signal que par le pipe, ce qui laissait de côté tout composant appelant `translate()` directement dans un
`computed()` (ex. `avatar.component.ts`, `difficulty-badge.component.ts`, `filter-pill.component.ts`…) — ces
textes restaient figés dans l'ancienne langue tant qu'aucune autre donnée ne changeait. Ne jamais réintroduire cette
lecture uniquement dans le pipe : tout nouvel appelant direct de `translate()` doit rester protégé sans rien faire
de spécial.

Voir `translate.service.spec.ts` (`should_make_any_computed_calling_translate_directly_reactive_to_a_language_change`)
et `translate.pipe.spec.ts` pour des tests de régression exerçant ce scénario (parent re-contrôlé pour une raison
indépendante, enfant `OnPush` contenant le texte traduit).

## 4. Règles de contribution

- Ajouter la clé dans **`fr.json` ET `en.json`** avant d'écrire le template — jamais dans un seul des deux fichiers
- Une clé manquante du dictionnaire actif retombe sur `fr.json` (RG-022-07) ; absente des deux, elle est renvoyée
  telle quelle et logue un avertissement en dev (détectable en test)
- Un test de parité (`frontend/src/app/core/i18n/dictionary-parity.spec.ts`) échoue si les deux dictionnaires n'ont
  pas exactement le même ensemble de clés, les mêmes paramètres `{{…}}` par clé, ou si une valeur est vide —
  exécuté à chaque `ng test`
- Les tests chargent les vrais dictionnaires (`provideI18nTesting()` / `provideI18nTesting('en')`) : un libellé
  attendu se vérifie par sa clé résolue (`t(key)` / `t(key, params, 'en')`), jamais par un texte dupliqué en dur
- Supprimer les clés orphelines des deux fichiers lors d'un refacto (script `npm run i18n:check` à prévoir — non
  encore créé ; le test de parité ci-dessus ne détecte pas les clés orphelines, seulement les divergences entre les
  deux fichiers)
- Pour ajouter une troisième langue : créer `<code>.json` avec la structure exacte de `fr.json`, l'ajouter à la
  constante des langues supportées (`Language` côté backend et frontend, `LANGUAGE_OPTIONS`) et une option radio —
  aucun autre changement de code n'est requis (`TranslateService` et `LanguageService` sont déjà génériques)
